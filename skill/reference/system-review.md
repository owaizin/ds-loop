# Review the system behind the product

Agent procedure for a whole-system assessment. Reuse discovery and inspect the
areas relevant to the user's outcome. A targeted request does not require a full
inspection. Engine results are one evidence source; they do not grade the team.

## Record the evidence boundary

Name the scope, source revision, representative consumers and evidence access.
Include code, design library when used, rendered behavior, documentation, tracker
and team reports. Separate unavailable evidence from evidence of a missing capability.
Use observed, reported, inferred, proposed and not checked labels near claims.

## Inspect the relevant areas

| Area | Question to resolve | Evidence to seek |
|---|---|---|
| Foundations and themes | Can supported modes and brands change without breaking roles? | Canonical sources, aliases, computed values, foreground/background pairs. |
| Components and patterns | Can the product's important tasks use the shared contracts? | Exports, supported states, production consumers, unmet needs. |
| Behavior and accessibility | Does the implemented experience meet its obligations? | Keyboard and focus checks, rendered states, tests and stated limits. |
| Design/code agreement | Are decisions represented consistently where the team works? | Design variables/instances, code APIs, version and naming differences. |
| Delivery and compatibility | Can changes reach consumers safely? | Packaging, builds, release policy, upgrade paths and rollback evidence. |
| Documentation and agent use | Can a newcomer find and apply the right contract? | Working imports, examples, normal entry points, fresh-task retrieval. |
| Ownership and contribution | Can an unmet need reach a decision and implementation? | Recent contribution records, exception owners, decisions and turnaround evidence. |
| Adoption and feedback | Do actual workarounds inform system changes? | Consumer measurements plus concrete support incidents, forks and backlog responses. |

For each inspected area, state what works, the demonstrated gap, competing
explanation, affected task, coverage and next action. No aggregate maturity score.
A quiet support channel does not establish satisfaction or disengagement; investigate.
Static import share is not satisfaction, runtime usage or delivery speed.

## Deliver the decision

Present the user's problem, what to preserve, the recommended intervention and its
alternative, followed by the first delivery and acceptance check. Each consequential
recommendation links to evidence and identifies remaining uncertainty. Put unresolved
questions beside the work they block. Keep the work list in the team's existing home.

Use [consult](consult.md) for the report and [adoption-plan](adoption-plan.md) when
replacement planning is needed. Before delivery, verify referenced records exist,
links resolve and every promised artifact is present or explicitly incomplete.
On a later review, gather fresh evidence before attributing change; compare only
compatible scopes. Close with [engagement](engagement.md)'s honest completion record.
