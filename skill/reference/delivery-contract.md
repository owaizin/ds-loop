# Make the finish line visible

Use the row matching the user's request before beginning its deliverable. Keep the
contract in the existing task record, not a new document for every small edit.
The detailed playbook remains authoritative for how to do the work.

| Request | Result the user can inspect | Proof before closing | Returning use |
|---|---|---|---|
| Discover / assess | Diagnosis, alternatives, recommended action and explicit unknowns | Claims have evidence and scope; first action has an observable finish line | Refresh changed sources and unresolved questions |
| Establish | Agreed foundations, real primitives/patterns, guide and maintenance paths | Build, rendered behavior, a real import, customization and extension checks from establish | A new contributor follows the normal entry point |
| Plan adoption | Pattern mappings, target API evidence, design/code effort and ordered slices | Every in-scope pattern has a disposition or named investigation; blocked work is separate | Refresh mappings after a slice or target-version change |
| Transform / migrate | Implemented authorized slices, updated contracts and remaining consumers | Preserved behavior, relevant builds/tests/renders, retained exceptions and rollback | Compare compatible evidence; do not restart discovery |
| Component contribution | Working public API, states, examples and consumer integration | Contract, behavior and accessibility checks appropriate to that component | Retained usage/extension guidance and release owner |
| Documentation / Storybook | Discoverable working reference linked to actual source | Build and rendered examples; preview parity or explicit difference; working links | Named refresh triggers and normal contributor entry point |
| Token architecture | Source/alias graph, contextual recommendations and adopted or proposed decisions | Resolve chains, modes and declared contrast pairs where supported; label unread/unresolved cases | Compare the same source/modes/config; reconsider changed consumers |
| Review / measurement | Scoped findings and coverage, including no-op if justified | Actual command results and relevant source/runtime checks; no implied repairs | Attributable baseline and remaining checks |

For each promised artifact, confirm it exists, opens and contains the required
information. Link to it in the completion record. A planned check is not a passed
check. Report delivered, verified and not checked separately. A review can finish
with open defects; implementation cannot claim checks that did not run.

## Visual explanations

Choose the smallest view that answers the decision: an evidence-backed report for
assessment, a source/alias map for token architecture, or a component-labeled sketch
for composition. Label whether each connection means an observed reference or a
proposed sequence. Link each consequential claim to evidence or mark it unverified.

For a composition sketch, inspect the real catalog/API before naming components.
Use the team's actual component names, show unsupported regions as unmapped, and
separate a proposed arrangement from existing production adoption. A sketch does
not establish responsive behavior, interaction or accessibility. When plain text
is sufficient, use a short labeled flow; do not require another visualization tool.
