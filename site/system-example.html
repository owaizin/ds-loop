What we changed

Both versions use the same product data. We changed the layout, controls, and labels by applying the conventions below.

AreaIndependent implementationsShared foundation
Page structureA legacy sidebar, top navigation, a separate billing portal, and a second member-management sidebar.A shared workspace shell, page header, and spacing rules.
ControlsFeature-specific colors, button shapes, search, and filter treatments.A common action style and matching control conventions.
Repeated dataCramped project rows, crowded request cards, inconsistent invoice and member lists.A common table structure, row density, and metadata hierarchy.
Status languageStatus treatments compete with content and vary between product areas.Shared labels and appearances for equivalent states.
Product differencesProjects have teams, Requests have priorities, Billing has invoices, and Members have roles.Each area keeps its own data and actions within the common structure.

Using Design System Loop for this work

Your team defines which patterns should be shared. The companion skill guides an agent through the relevant code, existing conventions, affected consumers, and verification. The engine supplies findings for the code it supports.

Your team and agent need to inspect the layout, content hierarchy, and status terminology. These require design judgment beyond the engine’s code checks.
