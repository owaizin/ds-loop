Build and maintain
your design system

Describe the outcome your product needs. Your agent investigates, recommends a scope, and delivers the work you authorize. These examples cover a first system, an existing gap, and a new contribution.

This guide includes the expanded setup procedure in the 0.2.1 source. npm currently provides 0.2.0. Use source installation to try the new procedure before publication. Installing either version does not activate your agent; ask it to read the skill.

Start a design system

Use this when your product needs a shared foundation. Agree which workflows it should serve, then build and adopt the system across that scope. If the product has no code yet, start from its brief and a representative use case.

Bring: related screens and flows, product constraints, and any existing visual direction.

Your agent does: inspect product needs, preserve suitable existing work, and choose a compatible foundation. Build the shared styles, controls, and compositions the agreed workflows need.

You receive: editable foundations and components used in the product, a reference built from the same source, and instructions for use, customization, contributions, and checks.

Review: whether the agreed workflows work, a shared style change reaches its consumers, and another contributor can find the guidance and extend a pattern. A first screen is a checkpoint unless the request was only for a pilot.

Improve a partial system

Use this when teams or features have accumulated competing versions of the same patterns. Compare connected areas, identify the intended conventions, and improve their shared foundation without erasing useful differences.

Bring: the affected product areas, shared components, known differences, and what your team expects.

Your agent does: trace existing patterns and their consumers, compare behavior, and make an authorized repair or explain why the difference should stay.

You receive: a checked change or a documented exception, with the reason and affected files.

Review: the intended improvement and any behavior that must stay unchanged. A shared-token change may affect other components.

Maintain an existing system

Use this to keep new features and contributions aligned with a system your team already trusts. Review shared-component changes and their consumers, and keep conventions and exceptions current.

Bring: upcoming changes, the affected component contracts and consumers, and previous decisions.

Your agent does: review the change against those commitments, run applicable code and behavior checks, and separate regressions from existing issues.

You receive: a review with source locations, results, and any decision needed before the change is ready.

Review: whether the change honors the system across its affected states and themes. Add edit feedback or CI checks after choosing the policy you want.

Make no code changes in this review. Link the decisions future contributors need to follow.

Explore the connected loops

Start with the product problem and existing commitments. Your agent uses the adoption loop to plan the work and the audit loop for code measurements. Enable the guard loop when you want feedback during edits.

Each loop below shows who does the work and what to review. The adoption loop includes steps for starting, improving, or maintaining a system.

Establish & improveAgent-guided · supervised alpha

Choose improvements based on the product’s needs and existing conventions. Scanner coverage tells you which code was checked; it cannot tell you how mature your design system is.

  1. Engine Gather measurements

    Run context . and an unfiltered audit . --json. Keep the report’s coverage with its findings.

  2. Agent + team Understand coverage and commitments

    Read relevant code, component contracts, and previous decisions. If the scanner cannot read a source or classify its naming, inspect it another way or state the limitation.

  3. Agent + team Choose the improvement

    Your starting point changes this step. An established system can still need a new convention in one area.

    Build and adopt the foundation

    Choose a suitable implementation base. Build shared foundations, components, and product patterns, then adopt them within the agreed scope.

    You receive: Editable source serving the agreed workflows, a working reference, and usage and maintenance guidance. The expanded procedure is in 0.2.1 source.

    Use the start prompt

    Apply an existing convention

    Trace the inconsistent UI to its intended pattern. Repair unintended drift, or preserve a difference that serves a real need.

    You receive: A verified change or a documented exception, with before/after evidence.

    Use the improve prompt

    Review against existing decisions

    Check new work against the component contracts and intentional exceptions already in use. Separate regressions from existing issues.

    You receive: A review with source locations, check results, and unresolved decisions.

    Use the maintain prompt
  4. Agent + team Verify the real flow

    Use the audit loop below for code checks and inspect affected UI, behavior, and accessibility with suitable tools. Separate pre-existing defects from regressions.

  5. Agent + team Save and reuse the decision

    Record the choice, evidence, limits, and when to revisit it. Link it from the project’s component documentation or contributor instructions. During an adoption pilot, check whether a fresh session can find and apply the decision from the normal repository entry point, without being given its path. A same-session reread does not establish retrieval.

Review these decisions when the same patterns change.

Audit a changeEngine + agent review

Use this loop within adoption or maintenance whenever a code change needs investigation and verification.

  1. Engine Orient and measure

    Use context for configuration and extraction scope; it runs no rules. Run an unfiltered audit for findings and checks that could not judge.

  2. Agent + team Interpret the result

    Check the project’s intended behavior and affected consumers. A scanner finding is a candidate for investigation, not permission to change code.

  3. Agent + team Change or preserve

    Make the authorized change, or explain why the existing behavior should stay. fix previews supported var() fallback insertions; it is not a general migration tool.

  4. Engine Rerun the unfiltered audit

    Compare findings and coverage under the same configuration. Changing the configuration changes the measurement.

  5. Agent + team Review the experience

    Check the affected states, themes, and behavior. Revise if evidence shows a problem; remaining findings may represent an intentional exception or a checker limitation.

Return to the change only when the evidence calls for it.

Guard an editOptional · Claude Code

This smaller loop runs during implementation. It supports the audit workflow; run an unfiltered audit at setup and before completion.

  1. Engine Install edit feedback

    Run ds-loop guard on in the target project. This installs a Claude Code PostToolUse hook.

  2. Agent + team Make a supported edit

    The edit has already landed when the hook runs. It cannot prevent or undo the change.

  3. Engine Audit the edited file

    Run a file-scoped audit at high severity. Also compare the project’s unread formats and unread token files with the previous observation.

  4. Engine Return feedback when needed

    Report high-severity findings. Announce an incomplete project extraction state on first observation or when it changes; ordinary saves remain quiet. Lower-severity judgment limits require an unfiltered audit.

  5. Agent + team Interpret and revise

    Review the result against the intended change and project conventions. If a further edit is needed, the hook checks again. CI gating is a separate policy.

The next supported edit starts this loop again.

Keep the decisions in your project’s documentation. Design System Loop has no central knowledge service; your team owns the records and the review and release process.

How the work comes back to you

Give your agent a concrete outcome and the scope it may change. It reads the project’s conventions, runs context and an unfiltered audit, and explains gaps that affect the review. Missing documentation does not mean your team has no conventions.

You provide Your agent returns
A screen, component, or proposed change The relevant code, existing patterns, and a baseline of current behavior
The behavior you want and what must stay the same A reasoned choice: establish a convention, change the code, or preserve a difference
The files it may edit and the team’s review requirements Changes within that scope, actual checks, and any unanswered questions
Where your team keeps decisions, if you have a place A linked record of the choice, evidence, and when to reconsider it

If you ask for guidance, the agent starts by understanding the problem and existing commitments. The number or severity of scanner findings does not choose the engagement for you.

The agent can carry out work you have already authorized. It asks when missing product intent or a wider change needs your decision. A scanner finding alone is not a reason to change the product.

Review the result

Check the behavior you asked for and the behavior that had to stay intact. For a visible change, compare the before and after in the browser. Read any remaining findings and coverage gaps. A lower finding count by itself does not establish a better product.

The handoff should link to the changed files, checks, and saved decision. Use your existing issue, component documentation, or decision directory; a new registry is not required.

Progress and handoff

The skill keeps the goal, evidence, and next action visible in the conversation. These are illustrative agent-authored notes, not CLI output or required templates. A small change can use a sentence; longer work needs an update when the scope, evidence, or next action changes.

While investigating 
Goal    Make the shared form usable in account settings
Scope   Account settings and its usage guide
[done]  Identify the consumer
[now]   Check the shared component’s behavior
[next]  Recommend the first change
Finish  A verified consumer and a working discovery path
When a decision changes the work 
Recommend  Repair the usage guide first
Evidence   Its import points to a removed export
Uncertain  Whether the component fits the consumer
Next       Check compatibility before migrating
At handoff 
Result         Usage guide repaired; migration deferred
[checked]      Documented import resolves
[not checked]  Consumer behavior in the browser
Continue       Verify the consumer before migration
Record         Link to the team’s existing decision

Implementation should prove a representative consumer, with working import and usage guidance. A token catalog or an isolated story does not prove adoption in the product. Keep failures and unrun checks visible, and link lasting decisions from the team’s existing documentation.

After a pilot, use its evidence to decide whether to expand to named consumers, adjust the approach, preserve the current implementation, or wait for a dependency. An ordinary handoff does not schedule future maintenance.

Get started

Install the published npm package, inspect your project, and load the companion skill in your agent. The setup guide includes the commands and a first prompt to adapt to your product.
