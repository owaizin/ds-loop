Fix a button’s dark theme.

A small, reproducible example of a token repair, with audit output, browser checks, and a saved decision.

Synthetic project · source included

1. Start with the intended behavior

Request: “The primary button should use our action palette in each theme. Fix the dark-theme background. Keep the light theme, button size, and markup unchanged.”

This example supplies that convention explicitly. It is an authored walkthrough using a small runnable project, not a customer result or an independent agent evaluation.

2. Inspect the current result

The dark theme defines a lighter blue, but the action token repeats the light-theme value. The button therefore stays the same color in both themes.

Visual and keyboard specimens only. These buttons do not save data.

:root {
  --palette-blue-500: #245bdb;
  --color-action-background: #245bdb;
}
.theme-dark {
  --palette-blue-500: #9ab8ff;
  --color-action-background: #245bdb;
}

The unfiltered audit reports color/semantic-holds-literal and color/literal-duplicate-tokens. Those findings help locate the problem. The requested theme behavior is the reason to change it.

3. Choose the smallest useful change

Reference the palette from the action token in each theme. This follows the supplied convention and keeps the button markup intact.

Changing the palette would affect other users of that color. Hardcoding the dark value would repair today’s appearance while leaving the action token disconnected from the palette. Neither is needed here.

/* In both :root and .theme-dark */
--color-action-background: var(--palette-blue-500, #245bdb);

Keep the reference in both selectors so it resolves against each theme’s palette. See the complete before CSS and after CSS.

4. Check the behavior

Check Before After
Light background #245bdb #245bdb (unchanged)
Dark background #245bdb #9ab8ff (follows palette)
Button size in the measured browser 129.20 × 43.59 CSS px 129.20 × 43.59 CSS px (unchanged)
Semantic literal and duplicate findings Present Absent

These colors and dimensions were measured in the browser. Keyboard focus reached the light-theme button and showed its outline after the change. The shared component CSS and markup were unchanged.

Remaining limit: the after-audit cannot classify these reference names with its default tier patterns. It reports token/tier-model-undetectable; the audit is not clean. The browser checks establish the requested theme behavior, not full accessibility or product coverage.

Run the same audits

From the repository checkout, after npm ci:

npm run ds-loop -- audit site/demo/before.css --json
npm run ds-loop -- audit site/demo/after.css --json

Both return findings and exit 1. These runs use the default configuration.

5. Document the decision

The deliverable includes the two-line token change, the before and after views, the checks above, and a saved decision.

The record states why the alias belongs in both themes and when to reconsider it. This page links to it so future contributors can find the reasoning. Finding it through an independent agent session has not been tested in this example.
